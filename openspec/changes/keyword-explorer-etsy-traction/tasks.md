# tasks — keyword-explorer-etsy-traction

## 1. User outcomes (from spec scenarios)

- [x] 1.1 A keyword with one matching listing shows its position
- [x] 1.2 A keyword with multiple ranking listings shows the best position
- [x] 1.3 A keyword with no ranking match shows a blank cell
- [x] 1.4 A keyword that is a tag on one listing shows its slot number
- [x] 1.5 A keyword tagged on multiple listings shows the earliest slot
- [x] 1.6 A keyword absent from every listing's tags shows a blank cell
- [x] 1.7 A minimum or maximum narrows the table
- [x] 1.8 A range filter applies to Ranked and Targeting the same as any other numeric column
- [x] 1.9 Status, Capture and Coverage are absent from the table
- [x] 1.10 The underlying data for all three is unchanged
- [x] 1.11 Blank cells sort after populated ones, not as zero

- [x] 3.6 `components/KeywordTable.tsx`: add `Ranked` and `Targeting` as right-aligned numeric sortable columns (blank cell, not `0`, when the row's value is `null`); remove `Status`, `Capture`, `Coverage` from the rendered `COLUMNS`/`<td>` set (props/row type keep carrying the fields — nothing is deleted from the data passed in). - [x] 3.8 Sort comparator: `null` (blank) sorts after every populated value regardless of direction, on Ranked and Targeting specifically — not the generic numeric sort's default of treating missing as `0`/lowest. (→ 1.11)

## 5. Copilot review round (2026-09-18)

Five real findings, all fixed and pushed; two more were self-caught while investigating one of them.

- [x] 5.1 **Real bug, highest severity of the round.** `read_spotted_on_etsy_csv`'s `int(... or 0)` fallback silently turned a blank Page/Position cell into the int `0` instead of dropping the row — the exact fabricated-zero failure mode `read_keyword_csv`'s own comment warns against, and a direct violation of this change's own "blank, never 0" rule (spec § Requirement: "A traction value with no match is visually and semantically distinct from a zero value"). Fixed: parse without a fallback (blank now raises `ValueError` and the row is dropped, matching `read_keyword_csv`), plus a new `page <= 0 or position <= 0` guard since a non-positive value is malformed, not a real low rank. Verified with a fixture CSV carrying two blank-field rows and one good row — confirmed only the good row survives. No change to `data/keyword-corpus.json`: the real `2026-09-17-erank-spotted-on-etsy.csv` has no blank Page/Position cells today, so this was a latent bug, not a live-data regression. (`scripts/ingest-pulls.py`)
- [x] 5.2 **Real gap.** `getLatestListingSnapshots()` returns the newest snapshot per listing across *all history*, so a deleted/deactivated listing keeps its last-known tags in that view — `computeTargeting` was reading all of them, meaning a keyword could show "Targeting" long after the listing that carried it stopped being live on Etsy. Fixed: `computeTargeting` now filters to `listing.state === "active"` before matching, mirroring the same field's use in `lib/etsy-listing-kit/evaluate.ts`. New tests: a tag on an `"inactive"` listing is excluded; a keyword still matches when at least one of several listings is active. (`lib/keyword-traction.ts`)
- [x] 5.3 **Real gap.** Targeting must be live on every request, but `app/keyword-explorer/page.tsx` never opted out of static rendering — `getLatestListingSnapshots()` is a Supabase read, not a Next.js dynamic API, so the segment was a static-rendering candidate that could bake `targeting: null` in at build time and never refresh. Fixed: `export const dynamic = "force-dynamic"`, matching the convention every other live-data page in this app already uses. (`app/keyword-explorer/page.tsx`)
- [x] 5.4 **Real gap.** The Supabase-failure silent-degrade path (design.md § Decisions) had no test exercising it — a regression could break it while every other test stayed green. Fixed: `withTargeting` exported (later moved to `lib/keyword-traction.ts` in round 2 — see 6.1); tests mock a rejected `getLatestListingSnapshots()` and assert every row's `targeting` comes back `null` without throwing, plus a happy-path test that a real match merges correctly. (`app/keyword-explorer/page.tsx`)
- [x] 5.5 **Real doc/implementation drift.** `design.md`'s Visual design table still said the range-filter inputs bind MVDS `Input`/`Field` and that `Badge` usage is unchanged — neither matches what shipped (plain `<input type="number">`; `Badge` removed along with Status). Fixed: row rewritten to state both deviations and why, rather than leaving an approved artifact silently wrong. (`design.md`)
- [x] 5.6 **Real test brittleness — self-caught while triaging 5.1–5.5, not a Copilot comment.** `tests/keyword-corpus.test.ts` asserted "every row's `ranked` is `null` today," which is the archive's current, transient state, not an invariant — the first future Spotted on Etsy pull that overlaps the corpus would fail this test despite correct behavior. This is the identical brittleness pattern #501 already fixed once (hardcoded snapshot instead of an invariant). Fixed: replaced with a shape check (null, or a well-formed `{best, matches}` where `best` equals the minimum position in `matches`) that holds regardless of how many rows currently match. (`tests/keyword-corpus.test.ts`)
- [x] 5.7 **Real doc inaccuracy — also self-caught, not a Copilot comment.** `proposal.md` claimed Targeting's live Supabase read is "the same read `etsy-zero-sales-funnel`'s scorecard page already ships in production." Checked: that page was never wired up (`etsy-zero-sales-funnel/tasks.md` §3.2 is still open) — the read exists and is unit-tested, but this change is its first live caller, not a second one. Fixed: corrected in place with the finding noted, rather than quietly rewritten. (`proposal.md`)
- [x] 5.8 **Test-quality fix — Copilot-suppressed (not separately posted), not a functional bug.** `KeywordTable.test.tsx`'s "no Status/Capture/Coverage column" test queried exact uppercase strings ("STATUS") against title-case rendered headers ("Status") — it would pass even if the columns were never removed, since that exact string was never going to render either way. Fixed: queries `columnheader` role elements case-insensitively, so a regression that reintroduced a column would actually be caught. (`tests/components/KeywordTable.test.tsx`)

## 6. Copilot re-review round (2026-09-18, second pass)

A fresh review requested after round 5's fixes. Eight more findings — three posted inline, five in the review body. All real except one, which was a genuine spec-wording ambiguity rather than a code defect; fixed by clarifying the spec instead of degrading working UI.

- [x] 6.1 **Real, high-value catch.** `withTargeting` was exported from `app/keyword-explorer/page.tsx` — a Next.js `page.tsx` is type-checked as a route module and may only export the default component plus recognised segment config (`metadata`, `dynamic`, …); an arbitrary named export there fails Next 16's generated route-type check on `next build` even though `tsc`/`vitest` (which don't run that check) stayed clean. Confirmed this repo is on `next@^16.2.10`. Fixed: `withTargeting` moved to `lib/keyword-traction.ts`; `page.tsx` now only exports `default`, `metadata` and `dynamic`. (`app/keyword-explorer/page.tsx`, `lib/keyword-traction.ts`)
- [x] 6.2 **Real hardening, same finding.** While moving `withTargeting`, its catch path returned the input `rows` unchanged on a Supabase failure rather than explicitly nulling `targeting` — harmless today (the one call site always passes freshly-loaded rows with `targeting: null` already), but not guaranteed once the function is an importable lib export a future caller could hand real Targeting data to. Fixed: catch path now maps every row to `targeting: null` explicitly. New test: a row that already carried a real Targeting value still comes back blank after a failed read. (`lib/keyword-traction.ts`)
- [x] 6.3 **Real gap.** `read_spotted_on_etsy_csv`'s blank/non-positive guard (round 5.1) had no committed test — I'd verified it with a one-off script, not permanent coverage. Fixed: new fixture-based describe block (`read_spotted_on_etsy_csv row-keeping, against a hand-built fixture`) with blank-Position, blank-Page, non-positive-Position and one valid row, asserting only the valid one survives. (`tests/keyword-corpus.test.ts`)
- [x] 6.4 **Real doc drift I'd missed on the first pass.** I fixed the Visual design table's MVDS `Field` mention in round 5.5 but missed an identical mention in the Decisions section two paragraphs down — same artifact, same contradiction, still present. Fixed: reworded to point at the Libraries/version row instead of restating (and this time getting wrong) the same fact twice. Also cleaned up an unedited thinking-out-loud fragment ("...status filter is gone too (see below), so...") left in the same paragraph from an earlier draft. (`design.md`)
- [x] 6.5 **Real loader-boundary gap.** `toRankedMatch`'s snake_case→camelCase mapping was only exercised end-to-end via `loadKeywordCorpus()` against the live corpus, which is all `ranked: null` today — the non-null branch (the actual field-by-field copy) had no direct test, so a typo'd field name would stay invisible until a real pull overlaps the corpus. - [x] 6.6 **Real fixture brittleness, same class as 5.6.** The Ranked-join fixture test (`tests/keyword-corpus.test.ts`) `copyFileSync`'d the real, committed `2026-09-17-erank-spotted-on-etsy.csv` into its temp dir rather than building its own — so a future re-pull changing "snow globe"'s real positions (or the file simply being superseded) would break this test despite correct behavior. Fixed: replaced with a fully synthetic Spotted on Etsy CSV the test owns outright, matching the hand-built-fixture pattern already used elsewhere in this file. Exact-value assertions (`.toBe(8)`) are fine again now that the fixture is fully test-owned, not live-data-dependent. (`tests/keyword-corpus.test.ts`)
- [x] 6.7 **Verified, not a defect — spec wording was genuinely ambiguous, fixed the spec instead of the code.** `formatTraction` renders an em dash for a `null` Ranked/Targeting value, and the spec's Scenario text said a blank cell must never show "0 *or any other placeholder value*" — read literally, that forbids the dash. But the em dash is this exact codebase's own pre-existing convention (`formatRatio`, same file, for `Searches / comp.` when competition is zero), and the Requirement's own summary line only ever promised the value stays "visually and semantically distinct from a zero value" — a dash satisfies that; a truly empty `<td>` would arguably read worse. Fixed: clarified both Scenario/Fails-until lines in `spec.md` to explicitly bless a non-numeric placeholder glyph, scoping the invariant to the underlying value (never rendering, sorting, or exporting as `0`) rather than to the DOM being literally empty. No code changed. (`specs/keyword-traction/spec.md`)

Merged its two tests into `tests/lib/keyword-traction.test.ts` alongside `computeTargeting`'s, and removed the now-empty `tests/app/` directory. (`tests/lib/keyword-traction.test.ts`)
