# keyword-explorer

## Human anchor

> "lets aggregate the data in a single table view on the hub. I want a datatable where I can sort and filter on all the fields we have. Assume that months from now I might drop new csv files for the same tag. And yes the data is often already filtered to remove obviously overcrowded keywords."

— Katy, 2026-09-17

## Outcomes

- **Who:** Katy, at the two moments the pull archive exists to serve — rewriting a listing, and deciding whether a product is worth making.
- **Job:** See every keyword observation the shop has ever captured as one table she can sort and filter on any field, and tell at a glance which observations are current and which are stale.
- **Done when:** every keyword CSV in `docs/pulls/` renders as one table; sort and filter work on every field; dropping a re-pull of the same seed months later adds its rows with no hand-editing and the table shows which observation supersedes which; and the hand-filtered nature of the exports is visible on the surface, so a missing keyword is never read as absence of demand.
- **Not doing:** charts, scoring, recommendations, or anything that writes back to Etsy. No ingestion of the non-keyword pulls (rankings, statements, ads) into this table — they have different grains and belong to their own surfaces. No replacement for the pull notes: the table holds rows, the notes hold the reasoning.

## Why

The landing zone is classified at the level of the **pull**, but not at the level of the **row**. `index.json` can tell you which capture measures demand; it cannot tell you what `embroidery fonts` scored, or that the same term appeared under four different seeds with four different tag-occurrence counts.

Both findings this data has produced so far — the demand gap, and the machine-embroidery hypothesis — came out of hand-diffing ten CSVs inside a single chat session. That analysis is now prose in a note. The rows behind it are not queryable by anyone, including the next agent session, and re-deriving it costs the same effort every time.

The re-pull case makes this worse rather than better. Ten CSVs are tractable by hand; forty, captured across six months, are not — and the comparison across captures is the entire point of keeping dated files rather than overwriting one.

## What changes

**A corpus, built from the archive.** `scripts/ingest-pulls.py` gains a step that parses every keyword CSV in `docs/pulls/` into `data/keyword-corpus.json`, regenerated by the same `--apply` run that already lands files and refreshes `index.json`. One command continues to be the whole ritual.

**One row per keyword × capture.** Average searches, competition and KD are keyword-scoped and agree across seeds within a capture. **Tag occurrences are seed-scoped and do not** — `embroidery font` read 80, 81, 12 and 6 across four seeds on 2026-09-17. So a row carries the seeds that surfaced it as a list, each with its own count, rather than flattening to one misleading number.

**Re-pulls extend the series, they don't overwrite it.** A second capture of the same seed adds rows. The default view is the current observation per keyword, with the change since the previous one; prior captures stay reachable rather than being replaced.

**The corpus is explicitly a curated subset.** Katy's exports are filtered by hand to drop obviously overcrowded keywords, so the archive is not a census and the table must not imply one. Concretely: nothing computes "disappeared" or "fell to zero"; a keyword's coverage reads as *seen in 2 of 3 captures*, not as a gap; and the surface says the corpus is filtered at capture time. A keyword absent from a later pull is unexplained, not extinct — and a table that quietly treats those as the same thing would manufacture exactly the false conclusions this archive exists to prevent.

**A hub route** renders it with sort and filter on every field.

## Capabilities

### New Capabilities

- `keyword-corpus`: the aggregated dataset and the rules that keep it honest — row grain, seed-scoped versus keyword-scoped fields, capture series and supersession, and the filtered-subset semantics that forbid inferring absence.
- `keyword-explorer`: the hub surface — a sortable, filterable table over the corpus, with staleness and coverage legible per row.

### Modified Capabilities

None. `docs/pulls/` conventions, `index.json` and the pull notes are unchanged; this reads the archive rather than altering it.

## Impact

- **New:** one route, one generated data file, one aggregation step inside an existing script, and a table component.
- **Unchanged:** every existing hub surface, the ingest script's current behaviour, and the landing-zone conventions merged in #498.
- **Open decision for `design.md`:** the repo has **no `components/ui/`, no shadcn, and no table library**, while `rules/design-guidelines.mdc` §2 says to default to shadcn/ui and names Table explicitly. Honouring that rule means this change introduces Radix, `cva`/`cn` and a headless table dependency as the repo's first shadcn surface. That is the right call by the written rule and a real cost; the alternative — a bespoke table — is what the same rule forbids. Flagged here rather than settled silently.
- **Blocked in Figma:** `keyword-explorer` (`pezlHOEjgdF1MUtYj7Jzbt`) is created and titled per the convention, but MVDS Core is not subscribed and does not appear in `libraries_available_to_add`. Frames wait on Katy toggling it on; `rules/figma.mdc` forbids bespoke chrome as a workaround.
